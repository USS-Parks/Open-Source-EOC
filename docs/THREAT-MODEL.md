# Threat Model (baseline, VEOC-04)

Living document. Every externally reachable surface planned in phases B-F is
enumerated here before it is built; the session that builds a surface updates
this file and adds the adversarial tests its row demands. Fail-closed (INV-7)
and total attribution (INV-2) are the standing mitigations everywhere.

## Assets

- **A1 Incident operational data:** boards, logs, sitreps, resource requests.
- **A2 Personal data:** tracking objects (patients, evacuees) carry
  HIPAA-adjacent details; damage assessments carry household details.
  Tracking and facilities are optional integrations, off by default, and are
  not reviewed for patient-level data in v1
  ([ADR-0009](./adr/ADR-0009-optional-integrations.md)).
- **A3 Audit integrity:** the append-only chronology is the legal record;
  its falsification is worse than its disclosure.
- **A4 Alerting authority:** the CAP/IPAWS path can page the public;
  misuse is a public-safety event, not a data event.
- **A5 Federation identity keys** and sharing agreements.
- **A6 Availability during activation:** the system is needed most when
  infrastructure is worst.

## Attacker classes

- **T1** Anonymous internet actor (scanning, abuse of public intake).
- **T2** Authenticated low-privilege user or mutual-aid guest exceeding scope.
- **T3** Compromised or hostile federation peer.
- **T4** Malicious plugin or board-template author.
- **T5** Insider with position access attempting to rewrite history.
- **T6** Supply chain (dependency or basemap/feed poisoning).
- **T7** Someone holding a shared, lost or stolen field device: the next
  person on a shift, or a finder with time and tools.

## Trust boundaries and surfaces

| # | Surface (session) | Faces | Primary risks | Standing requirements |
|---|---|---|---|---|
| B1 | REST `/api/v1` + WebSocket (VEOC-07..) | T1, T2 | authn bypass, tenant confusion, enumeration | server-derived principal; RLS second wall (ADR-0005); rate limits; deny-by-default routes |
| B2 | Public damage-report intake (VEOC-23) | T1 | spam, poisoning of assessed data, PII phishing | isolated intake store; moderation gate before it touches A1; rate limits; no account creation path |
| B3 | Federation ingest/egress (VEOC-27, VEOC-30), over the network and by file | T3 | forged payloads, scope creep, replay, poisoned records | the peer token checked before the body is read; every batch signed with the sending instance's Ed25519 key and verified under the key recorded for that peer before the agreement is read or anything applied, and a peer with no recorded key delivers nothing (ADR-0006); a batch file taken whole or not at all; per-record agreement scope check, and revocation; no sequence number: a replayed batch changes nothing, since updates merge and a deleted record stays deleted, and a batch file already imported is skipped by its digest; peer data always attributed, never merged anonymously |
| B4 | Collaboration adapters (conditional: `OPENEOC_INTEGRATIONS=collab`) | T2, T6 | token theft, membership drift, injection via chat content | routes and membership sync absent by default; adapter tokens scoped and stored server-side; membership reconciled from position assignments, one direction; chat content treated as untrusted text everywhere |
| B5 | Plugin sandbox | T4 | not applicable | no plugin runtime ships and no jurisdiction-authored code executes; board customization is declarative ([ADR-0004](./adr/ADR-0004-plugin-sandbox.md)). An executable plugin surface would need a new ADR and a new row here |
| B6 | Feed and sensor ingestion (VEOC-19, VEOC-26) | T1, T6 | spoofed feeds, malformed CAP/CoT parser attacks, staleness masking | feeds are read-only layers with provenance; schema-validated parse with fuzz tests; staleness always displayed |
| B7 | Outbound webhooks + notification channels (VEOC-14) | T2 | SSRF via webhook URLs, notification bombing, relay or provider credential exposure | per-jurisdiction destination allowlist, empty by default so nothing external is reachable, checked when a rule is created and again by the worker before each send; a host admitted by a `*.suffix` entry must resolve to public addresses, and a private, loopback or link-local target needs an exact-origin entry; http only for an exact loopback origin; redirects are not followed; HMAC signing; per-rule rate cap (default 60 per 10 minutes, at most 600 per window) with suppressed deliveries counted on a notification admins can see; email and SMS leave only through the relay and provider an admin configures for the jurisdiction, with the relay password or provider token envelope-encrypted and never returned; an HTTP SMS provider URL is held to the allowlist when configured and before each send; the SMTP relay is an admin-set host outside the allowlist, and a relay sign-in is refused without STARTTLS or TLS; recipients are people, not destinations, so addresses and numbers are not allowlisted, and each recipient counts against the rule's cap |
| B8 | Standards read surfaces: OGC Features, GeoJSON, HAVE export (VEOC-16, VEOC-28) | T1, T2 | permission leaks through the second representation | same authorization path as REST, tested for parity on every layer |
| B9 | IPAWS-OPEN connector (VEOC-31) | T2, T5 | unauthorized public alert issuance | disabled by default; separate enable authority; two-person rule on every send to the real endpoint, including the test handshake: one admin requests, a different admin confirms within 15 minutes, both recorded in the audit and the second-person check also held by a database constraint; full audit; test-environment fixtures only until an agency MOA exists |
| B10 | File library (VEOC-15) | T1, T2 | malware distribution, content-type confusion, storage exhaustion | content-addressed immutable storage; type allowlist; size quotas; no server-side rendering of uploads |
| B11 | Auth/identity (VEOC-07, VEOC-08) | T1, T2, T5 | credential stuffing, session fixation, position self-assignment | OIDC or local with rate-limited login; position assignment is an authorized act; mid-incident re-auth preserves state without widening it |
| B12 | Audit substrate (VEOC-11) | T5 | history rewrite, deletion, backdating | append-only at API and database (no UPDATE/DELETE grants on audit tables); server-side timestamps; corrections are new entries |
| B13 | Jitsi meeting bridge (conditional: `OPENEOC_INTEGRATIONS=meetings`) | T2, T6 | meeting-token theft, room guessing, unauthorized moderator access | routes absent by default; room names are random; JWT secrets stay in server-side envelopes; incident membership and role determine join authority |
| B14 | Object tracking and reunification (conditional: `OPENEOC_INTEGRATIONS=tracking`) | T2, T5 | disclosure of restricted person data, custody-event forgery, cross-jurisdiction search | routes absent by default; jurisdiction scope enforced server-side; restricted attributes require elevated membership; custody changes are attributed and audited |
| B15 | Facility status and HAVE exchange (conditional: `OPENEOC_INTEGRATIONS=facilities`) | T2, T6 | disclosure of HIPAA-adjacent capacity data, false status reports, stale availability | routes absent by default; jurisdiction scope enforced server-side; reports carry source and time; stale status remains explicit; exports use the authorized read path |
| B16 | Mass notification acknowledgement link, `GET` and `POST /api/v1/ack/:token`, no sign-in | T1, T2 | forged or guessed acknowledgements stopping a call-down, acknowledgement by a mail scanner, disclosure of the message or the recipient, token replay after the incident, bombing contacts through mass sends | each token is 128 random bits naming one recipient of one send, stored only as a SHA-256 hash; malformed tokens are refused before the database is asked; the link expires 24 hours after its message is sent; opening the link records nothing, only its button does, so a link-fetching scanner cannot acknowledge; the pages carry no message, name or address, a `no-store` cache header and a CSP with `form-action 'self'` and no script; 30 link requests per source address per minute beside the shared flood limiter; acknowledgement is written only by SECURITY DEFINER functions, the runtime role holds no update grant on it; mass sends need a member or admin, reach only the directory administrators keep, at most 500 people per send, audited as `notification.mass_sent` |
| B17 | Service identity tokens on REST `/api/v1` (VC-25) | T1, T2, T5 | token theft or guessing, reach beyond one jurisdiction, a token outliving its purpose or its creator, background work that outlives the identity, writes nobody can attribute, an integration widening its own access | 256-bit secret shown once and stored only as a SHA-256 hash that the runtime role can neither select nor get back from any function: the server hashes the presented secret and a SECURITY DEFINER function matches it; a token is checked before any lockout, so a valid one always passes, and five failed service tokens from one address answer 429 to that address's further failures for 30 seconds, beside the shared flood limiter; the authorization header is redacted from logs and no token or hash enters an audit payload; each identity acts through a flagged backing row with one membership, in its jurisdiction at viewer or member and never admin, so row-level security holds it with no policy of its own; triggers refuse that row a session, a second factor, a position, a guest grant, an incident participation or any other membership, and answer 403; sign-in, the people import and incident participation never find it; a viewer identity is refused every request that is not a read; the WebSocket channels and the person-only routes (marked `personSession` in the OpenAPI document) refuse its token; expiry is required and at most 366 days out; an identity acts only while it is not revoked or expired and its creator is still an enabled administrator of its jurisdiction, checked on every request (never cached) and by every background actor path (`principalForPerson` and scheduled report discovery; the other scheduler selections act only as administrators, which a backing row never is); revocation disables the backing row, and neither a revoked, expired nor creator-less identity can be enabled again; identities cannot create, list or revoke identities; every write is audited under the identity's own name; no step-up re-authentication exists in the product, so creation needs an administrator's session like every other administration act |
| B18 | What a device keeps for offline work (VC-27): the IndexedDB store (board documents, queued reports and files, the outbox, task completions, drafts, kept board forms and incident lists) and the signed-in session | T2, T7 | reading another person's cached incident data or unsent work, acting as the last person signed in, guessing the PIN through the app, copying storage to guess it elsewhere | **without a device PIN (the default) none of this is mitigated**: work sits in the clear store and the token pair and profile in localStorage, as before VC-27, readable by anyone with the device, and a restart opens the console as the last person; the console says so after every sign-in, in its side panel and in Settings, and offers the PIN, never requiring it. With a device PIN every value is AES-GCM encrypted under a random 256-bit data key, with a fresh IV and its store and key as associated data; the data key rests only wrapped under a key derived from the PIN by PBKDF2-SHA-256 (600,000 iterations, a 16-byte salt made on the device, the wrap bound to the person); setting the PIN moves the person's clear entries in and deletes them; the session's token pair and profile are sealed in the same store, never in localStorage; each person has their own key and store, another person's sign-in drops the key from the page, and a password sign-in opens a copy only with its PIN, unless the same person's PIN already opened it in that page; the console asks for the PIN at start and after 15 minutes without input; a wrong PIN is counted before it is tried, and from the third in a row a wait doubling from 30 seconds applies, both kept on the device so a reload does not reset them; the tenth erases the person's vault, then their store, unsent work included; the PIN and keys are never sent or logged. Open: whether a jurisdiction may require the PIN. Limits: a copy of the storage lets a six-digit PIN be guessed away from the app in minutes on one graphics card, so the operating system's disk encryption remains the defence for a lost device and longer PINs are advised; store keys (which name the person and incident), each vault's person name and wrong-PIN count, and viewer preferences are not encrypted; moving the device's clock forward shortens a wait but not the erase limit; erased data may stay in the browser's files until the browser compacts them |
| B19 | Esri interchange (VC-26): the read-only FeatureServer view `GET /api/v1/esri/rest/services/...`, and Esri JSON in the board import | T1, T2 | permission leaks through a third representation, a token carried in a URL or header reaching logs or a client's saved project, a person's session copied into a GIS project, writes through the view, record volume read from object ids, a crafted feature set exhausting the server, failing it, or storing an invalid shape | the view, the OGC items and the vector tiles read through one wall (`geo/layers.ts`): the caller's board role for field read levels, the map field included, so a board whose map field the caller may not read has no layer and is not listed on any of the three, and row-level security with record rules for records, so counts, ids, extents and features show only what the board shows the caller, tested for a service identity and a member; archived records are left out of the view; no write route exists (no `applyEdits`, every layer answers `capabilities: "Query"`), and a query takes only `where=1=1`, integer object ids and a numeric envelope, never SQL text; an envelope is converted to degrees in code, the whole world past 360 degrees and two boxes across the antimeridian; the token is accepted from `Authorization` on every route and, on these routes only, from `X-Esri-Authorization` or a `token` query parameter when it is a service identity's, then checked exactly as B17's bearer token, so revocation, expiry and the lockout hold, and a person's session is taken from `Authorization` alone; the request log line carries no query string, a logged request is serialized without one and `X-Esri-Authorization` is redacted, tested; the Windows host's Caddy log (whose proxy errors log the whole request) replaces the `token` query parameter's value (its name matched in any case or percent-encoding) and the acknowledgement link's path token (B16) with `REDACTED`, and drops the `X-Esri-Authorization`, `X-Peer-Token`, `X-Feed-Token`, `X-Intake-Token` and `X-Openeoc-Desktop-Token` headers, beside Caddy's own redaction of `Authorization` and `Cookie`, proved against the shipped Caddy; the guide tells administrators to send the token in `Authorization` where the client allows it, and that a token in a saved address lives in the client; each board numbers its own records through a trigger and a counter the runtime role cannot read, so an object id says nothing about other boards; a page is at most 1,000 records; the import is the board import (B1, `boards/transfer.ts`): a writer's act, 10 MB and 10,000 rows, every row validated as a new record against the board's field schema and write levels and written all or none, with its import report; a feature nesting deeper than Esri JSON does, fields that are not a list and attributes that are not named values are refused, and a date outside what a date can hold is a row error; only 4326 and 3857 are converted, any other spatial reference is refused rather than guessed, a coordinate past the edge of the world is refused, and every imported shape must pass PostGIS's validity check, with the reason on its row, never repaired |

## Standing adversarial test policy

Each session that opens a surface ships negative tests named for its row
(B1-B19) and they run in `pnpm check` forever. VEOC-37 re-verifies the whole
table adversarially before release.

## Out of scope (baseline)

Physical EOC security, OS hardening of the host, and denial-of-service by
carrier outage are deployment concerns documented at VEOC-40, not product
threat rows.
