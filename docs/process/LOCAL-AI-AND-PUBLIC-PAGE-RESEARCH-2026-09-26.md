# Research: local AI assistant and separate public page

Plain text notes for a follow-on plan. Every claim below has a source URL. Where a source is a vendor blog or a wiki-style writeup rather than a primary spec, that is noted.

## Feature 1: local AI assistant (draft-only, nothing leaves the machine)

### What competitors already do
- Juvare's JAI is an in-app assistant inside WebEOC that answers plain-language questions over incident data, aggregates records, and builds visualizations and reports. The wider Intelligence Suite adds Analyze (real-time dashboards) and Exchange (cross-org data sharing). Juvare also says the same suite can take a field damage photo and let AI populate the assessment record with structural classification and severity. Source: https://www.juvare.com/products/add-ons/intelligence-suite/ and https://www.juvare.com/thought-leadership/blogs/unveiling-jai-juvares-revolutionary-ai-assistant/
- Esri Survey123 added an AI image-analysis feature (beta, November 2025 release) that lets a form question run a custom prompt against a submitted photo to fill other fields automatically, for example classifying a photo as "illegal dumping," "graffiti," or "broken streetlight," or reading a license plate. Text and audio analysis (transcription) followed in the same beta wave. Source: https://community.esri.com/t5/arcgis-survey123-blog/make-your-survey123-forms-smarter-with-ai-powered/ba-p/1667044 and https://www.esri.com/arcgis-blog/products/survey123/announcements/whats-new-in-arcgis-survey123-march-2026
- Veoci's VIA is an opt-in assistant that can smart-fill forms, assemble after-action reports, and build tabletop exercises from source material. Source: https://veoci.com/on-demand-webinars/via-adaptive-operations-ai-veoci/
- Juvare achieved ISO/IEC 42001:2023 certification (the AI management system standard) in November 2025, covering risk management, AI impact assessment, lifecycle management, and third-party supplier oversight for its AI features; this is being extended to its FedRAMP High offering. Source: https://www.juvare.com/thought-leadership/news/juvare-achieves-iso-iec-42001-certification-strengthening-its-leadership-in-responsible-ai-for-critical-event-and-incident-management/

### (a) Local runtimes for a Windows/macOS sidecar
- llama.cpp is MIT licensed, written in C/C++ with no required Python runtime, ships pre-built binaries for Windows, macOS, and Linux, and includes a built-in OpenAI-compatible server mode (`llama-server`). It is optimized for CPU inference and also supports GPU acceleration. Source: https://github.com/ggml-org/llama.cpp and https://en.wikipedia.org/wiki/Llama.cpp
- Practical fit for OSS-EOC: llama.cpp (or a thin wrapper such as Ollama, also MIT licensed) can run as a child process the Fastify server spawns and talks to over localhost HTTP, keeping the AGPL-across-process-boundary rule satisfied for any GPL/AGPL-adjacent tooling and, more importantly here, avoiding vendoring a heavier Python ML stack. A quantized 7 to 8B model at Q4 (roughly 4 to 5 GB, see below) is a reasonable memory footprint next to Postgres and Node on a 16 GB laptop; a 3 to 4B model is the safer default for machines that also run the map and sync stack. No independent benchmark for "EOC laptop" hardware specifically was found in this pass; the CPU-speed claims above are vendor/community sourced, not independently reproduced, so plan to benchmark on real target hardware before locking in a default model size.

### (b) Small permissive text models for summarization and JSON/tool output
- Qwen2.5 (and its 2.5-VL and later Qwen3 siblings) 7B Instruct: Apache 2.0. GGUF Q4 quantized size is about 4.4 to 4.7 GB depending on the quant variant (Q4_0 vs Q4_K_M). Source: https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-GGUF and https://qwenlm.github.io/blog/qwen2.5/
- Mistral 7B Instruct (v0.2/v0.3): Apache 2.0, open for unrestricted commercial use. Source: https://mistral.ai/news/announcing-mistral-7b/ and https://huggingface.co/mistralai/Mistral-7B-Instruct-v0.3
- Microsoft Phi-4-mini-instruct: MIT license, 3.8B parameters, 128K context, 23 languages. Q4_K_M GGUF is about 2.5 GB, making it the lightest of this group at good quality. Source: https://huggingface.co/microsoft/Phi-4-mini-instruct (license) and https://huggingface.co/bartowski/microsoft_Phi-4-mini-instruct-GGUF (quant sizes)
- IBM Granite 3.0: Apache 2.0 across the family, including 2B and 8B dense models and smaller MoE variants aimed at constrained hardware. IBM markets it specifically for enterprise tool-use and RAG workloads. Source: https://github.com/ibm-granite/granite-3.0-language-models and https://www.ibm.com/new/announcements/ibm-granite-3-0-open-state-of-the-art-enterprise-models
- Quality notes: Qwen2.5/Qwen3 7B and Granite 8B are both regularly cited as strong at structured (JSON/tool-call) output and summarization for their size class; Phi-4-mini trades some raw capability for a much smaller footprint. All four are legitimate Apache-2.0/MIT candidates; none require the custom-license flag.
- Explicitly not permissive for this use: Meta's Llama 3.x models carry the Meta Llama Community License, a custom (non-OSI) license with a redistribution notice requirement and a "Built with Llama" attribution obligation, so it needs legal review before being vendored into an installer. Source: https://www.llama.com/llama3_1/license/. Google's Gemma models have historically shipped under a custom Gemma Terms of Use with a prohibited-use policy rather than a stock OSI license; treat any claim that a newer Gemma release moved to plain Apache 2.0 as unverified until checked against Google's own model card at release time, since it would be a change from the pattern in every earlier Gemma release. Source (background on the custom-license pattern): https://blog.promise.legal/open-weight-ai-license-trap-startups/

### (c) Vision-language models for damage photo classification
- Qwen2.5-VL: the 7B-Instruct variant is Apache 2.0 for commercial and non-commercial use; the 3B variant's license is more restrictive (research/non-commercial framing in some summaries), so standardize on the 7B if a single VL model is vendored. Source: https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct and https://www.deeplearning.ai/the-batch/alibaba-debuts-qwen2-5-vl-a-powerful-family-of-open-vision-language-models
- Microsoft Florence-2: MIT licensed, base (~230M) and large (~770M) parameter sizes, unified prompt-based model that does captioning, detection, grounding, and segmentation. Its small size makes CPU inference realistic, though it is a lower-level vision model rather than a chat-style VLM, so damage classification would need a thin prompt/label layer on top rather than free-form Q&A. Source: https://huggingface.co/microsoft/Florence-2-large
- SmolVLM (Hugging Face): Apache 2.0, variants from 256M to 2.2B parameters, explicitly designed for on-device and CPU deployment. Source: https://huggingface.co/blog/smolvlm
- Moondream: the original Moondream 2B/0.5B line is Apache 2.0 and the 0.5B variant is small enough to run in under 1 GB of memory in int4. However, the newer Moondream 3.1 release switched to the Business Source License 1.1 with an additional-use restriction, which is source-available, not permissive, and fails the redistribution requirement. If Moondream is used, pin to the Apache-2.0 2.x line and do not upgrade to 3.x without a license re-check. Source: https://moondream.ai/models and https://moondream.ai/blog/introducing-moondream-0-5b
- No independently published benchmark of these specific models against real disaster-damage photos was found in this pass (see dataset note below); treat "damage type and severity from a photo" as a prompt-engineered classification task on a general small VLM, validated against a labeled local sample before trusting it for records.

### (d) Embeddings and local semantic search
- nomic-embed-text: Apache 2.0, 137M parameters, about 274 MB, 768 dimensions, 8K context, runs on CPU. This is a common Ollama default and a reasonable fit for embedding SITREPs, incident notes, and AAR text. Source: https://localaimaster.com/models/nomic-embed-text and https://docs.nomic.ai/atlas/embeddings-and-retrieval/generate-embeddings
- BGE-M3 (BAAI): MIT licensed, multilingual (100+ languages), 8K context, supports dense/sparse/multi-vector retrieval in one model; bge-small-en-v1.5 is a much smaller (33M parameter) English-only alternative if multilingual coverage is not needed. Source: https://d-central.tech/local-embedding-models/
- pgvector: PostgreSQL License (a permissive BSD-style license), and OSS-EOC already runs PostgreSQL, so pgvector is the natural fit rather than adding a separate vector store. Source: https://github.com/pgvector/pgvector/blob/master/LICENSE
- Recommendation on search approach: for a first pass, Postgres full-text search (tsvector/tsquery, already built in, zero new dependency) is enough for keyword-style incident search and is the laziest correct option. Add pgvector plus a small embedding model only when semantic ("find records like this one" or natural-language) search over incident text is an explicit requirement, since it adds an embedding pipeline (re-embed on write, re-embed on model upgrade) that plain full-text search does not need.

### (e) Damage-assessment evaluation data and known limits
- xBD is the standard published dataset for building damage assessment from satellite imagery: 850,736 building annotations across a 45,362 km2 area and multiple disaster types, built for the DIU/xView2 challenge. Source: https://arxiv.org/abs/1911.09296 and https://www.diu.mil/latest/assessing-building-damage-from-satellite-imagery
- License caution: xBD/xView2 data requires registration through xview2.org and at least one source describes it as CC BY-NC-SA, a non-commercial share-alike license; this is a dataset licensing question (training/eval data), separate from the model-weight redistribution rule in the project's constraints, but it still means xBD imagery itself should not be redistributed inside the installer or product, only used, if at all, for offline internal evaluation. Source: https://github.com/DIUx-xView/xView2_baseline/blob/master/LICENSE.md
- xBD and FEMA's four-category damage scale (Affected, Minor, Major, Destroyed, plus Inaccessible) are satellite/aerial-imagery and structure-level scales; they are a reasonable reference for category *names* but were not built for close-up field photos of a single building or room, which is the actual OSS-EOC use case, so treat any of the small VLMs above as needing local validation against real field-photo examples rather than assuming xBD-trained accuracy carries over. Source: https://www.fema.gov/sites/default/files/documents/fema_pda_individual-assistance-damage-matrix.pdf

### (f) Governance
- Juvare's public framing of ISO/IEC 42001 emphasizes risk management, AI system impact assessment, lifecycle management, and third-party supplier oversight, with "strong human oversight" called out explicitly. Source: https://www.juvare.com/thought-leadership/news/juvare-achieves-iso-iec-42001-certification-strengthening-its-leadership-in-responsible-ai-for-critical-event-and-incident-management/
- Practical controls worth adopting, drawing on the above and on general RAG security guidance: (1) every AI output in the product is a draft that a human must explicitly approve before it becomes part of the official record, never auto-saved; (2) AI-authored or AI-assisted text and photo classifications carry a visible provenance label (model name, version, timestamp) wherever they appear; (3) every AI invocation is logged (input reference, output, approving user, timestamp) to the same audit trail as other record edits; (4) because incident records, SITREPs, and AAR text are attacker-reachable free text, treat them as untrusted input to the assistant and keep instructions and retrieved content separated in the prompt, since indirect prompt injection through retrieved documents is a documented, high-success-rate attack against RAG systems (one study found 5 poisoned documents in a corpus reached a 90 percent attack success rate). Source: https://www.vectra.ai/topics/prompt-injection and https://genai.owasp.org/llmrisk/llm01-prompt-injection/

### Recommended stack, feature 1
- Runtime: llama.cpp server (MIT) as a local sidecar process, spawned and supervised by the Fastify server, talking over localhost HTTP only.
- Text model default: Qwen2.5 7B Instruct, Q4_K_M GGUF (Apache 2.0, about 4.7 GB), with Phi-4-mini-instruct (MIT, about 2.5 GB Q4_K_M) offered as a low-memory fallback for lighter hosts.
- Vision model: Qwen2.5-VL-7B-Instruct (Apache 2.0) for damage photo classification, with SmolVLM (Apache 2.0) as the CPU-lightweight fallback; do not use Moondream past the 2.x line while it stays on BSL 1.1.
- Search: Postgres full-text search first; add pgvector (PostgreSQL License) with nomic-embed-text (Apache 2.0) only once semantic search is a confirmed requirement.
- Governance: human-approval gate on every AI output, provenance labels, full audit logging, and prompt/content separation to blunt indirect prompt injection from incident text.
- Every model and runtime named above is Apache-2.0, MIT, or PostgreSQL-licensed and is redistributable inside an offline Windows/macOS installer; Llama and Gemma weights are explicitly excluded per the custom-license flag in the brief.

## Feature 2: separate public page (read-only shelter/evacuation status, moderated damage report queue)

### What competitors already do
- Esri's Emergency Shelter Management solution ships an Occupancy Count form for shelter staff and a Registration Management app for guest check-in/out, with shelter data supporting facility capacity ("Evacuation Capacity," based on 20 square feet per person), pet accommodation codes (e.g., a "COHABIT" value meaning pets can stay with their owners), and accessibility flags such as ADA-compliant/wheelchair-accessible. Source: https://www.esri.com/arcgis-blog/products/arcgis-solutions/emergency-management/emergency-shelter-management and https://gis.fema.gov/arcgis/rest/services/NSS/FEMA_NSS/FeatureServer/13 and https://gis.fema.gov/arcgis/rest/services/NSS/FEMA_NSS/FeatureServer/12
- Esri's Damage Assessment solution includes an ArcGIS Hub public site that shares assessment status with the community and collects resident-submitted damage reports, which staff then triage through a separate Damage Assessment Operations app; Esri's page did not publish a detailed field list for the public intake form. Source: https://www.esri.com/en-us/industries/emergency-management/solutions/damage-assessment
- Juvare Crisis Track's public "Damage Self Report" form (a live example from VDEM) asks for: report type (residential or business), the emergency event, address and 5-digit zip, a free-text damage description, checkbox damage types (structural, off-foundation, roof, chimney, HVAC, well/septic, flood water level, tree damage, driveway, debris), insurance status (yes/no/don't know), business-confirmation and business-name fields, photo upload, and reporter contact info (name, phone, email). Source: https://crisistrack.juvare.com/public/VDEM/request.html
- California has standardized wildfire evacuation terminology into three tiers: Evacuation Order (immediate threat, leave now, area closed), Evacuation Warning (potential threat, leave now if you need extra time or have pets/livestock), and Shelter in Place (go indoors, seal up, wait for instructions); many counties also use the parallel "Ready / Set / Go" framing (Level 1/2/3). A statewide evacuation-zone lookup-by-address platform is used by CAL FIRE and many counties. Source: https://calalerts.org/evacuations.html and https://firerisk.ai/fire-evacuation-map

### Fields and conventions to reuse
- Shelter status page: shelter name, address/location, open/closed status, current occupancy vs. capacity, pet-friendly flag (with cohabit vs. separate-area distinction), ADA/wheelchair accessibility flag, and a last-updated timestamp. Source: same Esri/FEMA links above.
- Evacuation status: zone identifier plus a status of Order, Warning, or Shelter in Place (or the county's local equivalent labels), searchable by address, matching the CAL FIRE-style pattern. Source: https://calalerts.org/evacuations.html
- Public damage self-report: report type, event/incident name, address and zip, free-text description, categorized damage-type checkboxes, photo upload, insurance status, and optional contact info; make contact info optional rather than required so the form does not become a de facto identity-collection tool. Source: https://crisistrack.juvare.com/public/VDEM/request.html

### Accessibility and language
- Federal Section 508 still cites WCAG 2.0 AA as its technical standard, but most federal and state bodies now design to WCAG 2.1 or 2.2 AA in practice; DOJ's 2024 Title II rule requires state and local government web content and apps to meet WCAG 2.1 AA on a phased timeline, with compliance due by April 24, 2026 for larger jurisdictions. Building to WCAG 2.2 AA now covers both the current legal floor and near-term best practice. Source: https://www.levelaccess.com/compliance-overview/section-508-compliance/ and https://juiceboxinteractive.com/blog/accessibility-guide/
- Multilingual expectations: the FCC's Multilingual Alerts Order (adopted January 2025) will require Wireless Emergency Alerts to support pre-translated templates in 13 languages beyond English (Arabic, Chinese, French, German, Haitian Creole, Hindi, Italian, Korean, Portuguese, Russian, Spanish, Tagalog, Vietnamese) plus ASL, phased in through June 2028; this is a strong signal of the language set a county EOC's own public page should plan to support at minimum for its highest-priority content (shelter status, evacuation levels), even though the rule itself governs carrier alerts, not county websites. Source: https://www.fcc.gov/multilingual-wireless-emergency-alerts

### Abuse and privacy controls for public damage intake
- Accessible bot defense: prefer invisible mechanisms (honeypot fields, proof-of-work/invisible challenges like Cloudflare Turnstile's invisible mode) over visible image challenges, since visible CAPTCHAs are hostile to screen-reader and low-vision users; pair a honeypot with a render-time nonce (reject submissions that arrive implausibly fast) and server-side rate limiting by IP/session, since honeypots alone only stop unsophisticated bots. Source: https://friendlycaptcha.com/insights/captcha-alternative/ and https://www.digitalapplied.com/blog/form-bot-defense-honeypot-first-playbook
- PII handling: treat name/phone/email on the damage form as optional and minimize retention; DHS/NIST guidance frames PII risk as scaling with how widely it is accessed, shared, or transmitted, which argues for keeping the public-facing intake as small and short-retention as possible and moving anything sensitive into the protected system rather than the public review queue. Source: https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-122.pdf
- Location fuzzing: no county-specific published standard was found for fuzzing self-reported damage locations; the general privacy pattern from PIA guidance is to publish only what is operationally necessary (e.g., street/block or a snapped-to-parcel point) rather than an exact GPS pin, and to hold precise coordinates in the moderated/internal queue only until a report is verified and merged into the protected system. Treat this as a design default to confirm with the project owner, not a sourced industry standard.

### Static, scheduled publishing
- PMTiles is a single-file tile archive format designed to be served from plain static storage (a web host, object storage, or GitHub Pages) with no tile server required, using HTTP range requests and rendering via MapLibre GL JS, which matches OSS-EOC's existing map stack. Source: https://github.com/protomaps/pmtiles and https://til.simonwillison.net/gis/pmtiles
- A scheduled refresh is a plain scheduled job (a documented example uses a GitHub Actions cron trigger, with a manual workflow_dispatch escape hatch) that regenerates the static HTML/PMTiles bundle from the protected system's data and pushes it to whatever host serves the public page; the same pattern works from an internal Windows Task Scheduler job if GitHub Actions is not desired, since the mechanism is just "run an export script on a schedule, then copy files to a web host." Source: https://github.com/protomaps/PMTiles/discussions/289

### Recommended stack, feature 2
- Output format: static HTML plus a PMTiles map bundle (protomaps/PMTiles, BSD-3-Clause per the repository) rendered with MapLibre GL JS (BSD-3-Clause), exported on a schedule by an authorized user's action or a scheduled task from the protected system, published to any web host.
- Shelter/evacuation page: read-only, fields per the Esri/FEMA pattern above (status, capacity/occupancy, pet and ADA flags, last-updated) plus a zone-status lookup using the Order/Warning/Shelter-in-Place vocabulary.
- Damage intake: short form (event, address, description, categorized damage type, photo, optional contact) feeding a moderated review queue, never the live protected system directly.
- Accessibility: WCAG 2.2 AA as the build target; language support at minimum for the FCC's 13-language WEA set for the highest-priority content blocks.
- Abuse controls: honeypot plus invisible challenge plus server-side rate limiting, no visible CAPTCHA; minimal, optional PII; fuzzed or parcel-level public location display with precise coordinates held only in the internal moderation queue.
